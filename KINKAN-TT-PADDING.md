# Эксперимент: паддинг TrustTunnel

Реализация пункта 14 ROADMAP.md для проверки гипотезы о распознавании размеров
«TLS внутри TLS». Результата замера на мобильном МТС пока нет: локальные тесты
проверяют совместимость и HTTP/2, а не эффективность против ТСПУ.

## Что меняется

Только TCP-фронт TrustTunnel включает случайный паддинг исходящих HTTP/2 DATA:
0–255 нулевых байт на кадр, длина выбирается через `crypto/rand`. При длине 0
кадр всё равно получает PADDED и байт Pad Length=0. Клиент выбрасывает паддинг
по [RFC 9113, §6.1](https://www.rfc-editor.org/rfc/rfc9113.html#section-6.1).
Клиенты, входящие DATA, HTTP/1.1, HTTP/3 и остальные фронты не меняются.

Перед разделением DATA в `Consume` сервер резервирует и списывает паддинг
вместе с байтом длины из окон потока и соединения. Полный кадр делится так,
чтобы весь payload помещался в MAX_FRAME_SIZE. Когда оставшееся окно или
бюджет планировщика не вмещает паддинг, сервер отправляет данные без него.
Пустые завершающие DATA могут оставаться без паддинга.

Обычная и асинхронная запись используют один и тот же паддинг. Размер буфера
и размер DATA для планировщика включают его. Только обработчик TT имеет
маркер включения; остальным пользователям `metacubex/http` он не добавляется.

## Как выключить без пересборки

По умолчанию эксперимент включён. Задать **в окружении процесса ноды**:

```sh
KINKAN_TT_PADDING=0 mikan-node ...
```

Для Docker добавить `KINKAN_TT_PADDING: "0"` в `environment` сервиса ноды
и пересоздать контейнер. Для systemd — `Environment=KINKAN_TT_PADDING=0`
в секции `[Service]`, затем перечитать unit и перезапустить ноду.
Переменная на панели не изменяет окружение удалённых нод.
Чтобы вернуть паддинг, удалить переменную либо поставить `1` и перезапустить.

## Проверки

```sh
scripts/tt/mihomo.sh --check
scripts/tt/http.sh --check
(cd third_party/metacubex-http && go test -run TestKinkan .)
(cd third_party/metacubex-http && go test . ./http2/... ./h2c/... ./httptest/...)
(cd third_party/mihomo && go test ./transport/trusttunnel/... ./listener/inbound/...)
go test github.com/metacubex/mihomo/transport/trusttunnel/... github.com/metacubex/mihomo/listener/inbound/...
go test -run 'TestTrustTunnel|TestHysteria2ScannerAuthOnNode' ./internal/node
```

Тест HTTP/2-клиента той же библиотеки передаёт три параллельных потока по
3 360 000 байт, проверяет побайтное совпадение, PADDED и разные длины на проводе.
Проверены обычное окно и 16 КиБ, отключение переменной и отсутствие паддинга
на другом фронте. Отдельные проверки покрывают границы обоих окон,
MAX_FRAME_SIZE, бюджет планировщика и завершение разделённого потока.
Тест реального TT-фронта скачивает через HTTPS/fallback по несколько мегабайт
с окном 16 КиБ при включённом и выключенном эксперименте.

При локальном запуске всего `go test ./...` зависимости на Go 1.27.2 падают
два существующих теста `httputil`:
`TestReverseProxyQueryParameterSmugglingDirectorParsesForm` и
`TestReverseProxyQueryParameterSmugglingRewrite`. То же падение воспроизведено
на исходном `main` без эксперимента. Затронутый пакет сервера и остальные
пакеты HTTP-библиотеки проходят; `httputil` этим изменением не исправляется.

Изменения зависимости воспроизводятся патчами и скриптами; вручную править
`third_party` не нужно. Новая логика находится в `kinkan*.go`.

## Сравнение на живой ноде

С одной сборкой повторить одинаковые подключения с мобильного МТС:
сначала `KINKAN_TT_PADDING=0`, затем с паддингом. Записать число удачных
подключений, время до блокировки и размеры внешних TLS-записей в локальном
pcap. Повторить несколько раз и сравнить с AnyTLS на той же ноде.
Измерения сохраняет оператор; код не собирает и не отправляет телеметрию.

Этот эксперимент меняет направление сервер → клиент. Если блокировка нового
ClientHello формируется независимо от предыдущего трафика в этом направлении,
он может не помочь. Паддинг HTTP/2 также не гарантирует изменение границ внешних
TLS-записей: это необходимо проверить захватом трафика.
