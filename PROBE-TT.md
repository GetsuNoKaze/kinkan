# Проверка TrustTunnel «глазами сканера»

Команда появится в следующем релизе после `0.5.0.5-tt.3`. В исходниках она уже есть.
На установленной панели **и на отдельной ноде**:

В админке: **Ноды → Проверка TrustTunnel** в карточке нужной ноды. Выберите
включённое подключение TrustTunnel и HTTPS-порт cover-сайта (обычно `8444`);
пустое поле отключает сравнение. Отчёт можно скачать в JSON. Запуск доступен
только админской сессии с CSRF, не API-ключу и не клиентам подписок.

Запросы идут **с сервера панели** на публичный адрес ноды. Это не проверка пути
из сети пользователя через ТСПУ. Адреса берутся из сохранённых настроек ноды;
DNS проверяется и IP закрепляется на весь запуск, внутренние адреса не допускаются.
На панели один запуск за раз; общий предел 75 секунд, каждый запрос до 2 секунд.
Закрытие окна прерывает запрос, таймаут сохраняет полученные результаты и `ERROR`.
Если HTTPS-порт cover-сайта доступен только локально на ноде, сравнение с панели
не выполнится: используйте открытый HTTPS listener или CLI на наблюдателе с доступом.

Через команду:

```sh
kinkan probe --reference https://flowers.example.org:8444 https://flowers.example.org:443
```

Замените адреса: последний — HTTPS-порт TrustTunnel, `--reference` — настоящий
HTTPS-сайт Caddy/nginx, который обслуживает то же содержимое, что HTTP fallback.
Это может быть текущий HTTPS listener Caddy для REALITY. Сертификаты обоих адресов
должны быть доверенными и подходить доменам; отключения проверки сертификатов нет.
Для проверки ноды из другой сети запускайте команду на наблюдателе, где установлен
Kinkan, или используйте исходники. Проверка с самой ноды не воспроизводит путь через ТСПУ.

Без установленного Kinkan (нужен Go из `go.mod`):

```sh
go run ./cmd/mikan probe --reference https://flowers.example.org:8444 https://flowers.example.org:443
```

Если эталон недоступен, `--reference` можно опустить. Тогда команда проверит явные
признаки proxy-auth и напечатает HTTP/2 отпечаток, но предупредит, что сравнения не было.
Флаги ставятся **до** последнего адреса:

```sh
kinkan probe --json --timeout 3s --reference https://flowers.example.org:8444 https://flowers.example.org:443 >probe.json
```

## Что проверяется

33 проверки, последовательно, без настоящего пароля:

- Четыре TLS handshake: без ALPN, только `http/1.1`, только `h2`, оба варианта.
  Выводятся согласованный протокол, версия TLS, издатель, SAN и срок сертификата.
- Два диагностических handshake: без SNI и с `kinkan-probe.invalid`. Они намеренно
  не проверяют сертификат: отказ или сертификат default vhost допустимы и выводятся
  как `INFO`. Обычные подключения всегда проверяют цепочку и имя сертификата.
- Сырая преамбула HTTP/2 при отсутствующем ALPN и при согласованном `http/1.1`.
  Ответ HTTP/2 SETTINGS в таком соединении — `FAIL`; ответ HTTP/1 — `PASS`.
- По 12 запросов через HTTP/1.1 и HTTP/2: GET, HEAD, OPTIONS, CONNECT, неверный
  Basic, повреждённый Basic, Bearer, CONNECT с неверным Basic, `robots.txt`,
  `favicon.ico`, `security.txt` и отсутствующая страница. Ищутся `407` и наличие
  `Proxy-Authenticate`, даже если его значение пустое.
- HTTP/2 отпечаток: порядок и значения SETTINGS, WINDOW_UPDATE до первых
  заголовков ответа, порядок имён заголовков после декодирования HPACK.

При `--reference` те же запросы отправляются эталону с **Host/:authority цели**,
чтобы сравнивать один vhost. TLS SNI эталона берётся из его собственного адреса.
Сравниваются статус и SHA-256 полного тела ответа. Для HTTP/2 сравнивается отпечаток.
Динамические страницы, разные правила vhost, HEAD/CONNECT или нестабильный порядок
заголовков могут давать отличия — они требуют разбора, а не доказывают наличие прокси.
Обычные заголовки по значениям не сравниваются (например, Date меняется).

## Чтение результата

- `FAIL` — явный proxy-auth ответ или HTTP/2 без согласования `h2`.
- `ERROR` — проверка не выполнена: сеть, сертификат, таймаут, некорректный HTTP/2
  или ответ слишком велик. Это не успешная проверка.
- `WARN` — отличие от сайта, необычный ALPN/ответ или отсутствующее сравнение.
- `PASS` — конкретная проверка пройдена; `INFO` — диагностическое наблюдение.

Код завершения `1` при любом `FAIL` или `ERROR` (также при ошибке аргументов), `0` —
при отсутствии этих двух категорий. **WARN не меняет код завершения:** автоматизация
должна отдельно смотреть `findings[].level` в JSON, если ей нужен строгий эталон.
Успех не означает невидимость для всех сканеров и не гарантирует обход блокировки.

Перенаправления не выполняются, системный HTTP proxy не используется. Каждое
подключение ограничено `--timeout` (по умолчанию 5 секунд, допустимо 100ms–30s),
тело ответа — 2 MiB, HTTP/2 заголовки — 64 KiB, кадры до ответа — 128.
С эталоном выполняется до 58 подключений; при недоступных адресах проверка может
занять несколько минут. Ctrl+C прерывает работу. Команда не меняет конфигурацию
ноды, но пробы могут попадать в access log и лог неверных паролей.
